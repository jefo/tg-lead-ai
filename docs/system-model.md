# Системная Модель: AI-Стратег v1.0

**Система Интереса (System of Interest):** Телеграм-бот "AI-Стратег"

**Миссия Системы:** Трансформировать неопределенность потенциального клиента в ясный, обоснованный и вызывающий доверие план маркетинговых действий, эффективно квалифицируя клиента для дальнейшего взаимодействия.

## L1. Операционный Анализ: Стейкхолдеры и их Потребности

| Стейкхолдер | Описание | Ключевые Потребности (Needs) |
| :--- | :--- | :--- |
| **"Марк" (Пользователь)** | Владелец SMB, ищущий предсказуемый маркетинг. Не доверяет "черным ящикам". | **N-01:** Получить понятный, персонализированный план действий, а не общие слова<br>**N-02:** Понимать логику (`почему?`) предложенной стратегии, чтобы доверять ей<br>**N-03:** Не тратить время на сложный интерфейс или бессмысленные вопросы<br>**N-04:** Получить ощутимую ценность немедленно, без обязательств и передачи контактов |
| **"Инди-хакер" (Владелец Системы)** | Эксперт, который хочет продемонстрировать свой "не-наивный" подход и получить качественные лиды. | **N-05:** Система должна эффективно отсеивать нецелевых клиентов и квалифицировать целевых<br>**N-06:** Система должна демонстрировать глубину экспертизы (стратегический подход, а не просто кодинг)<br>**N-07:** Система должна быть построена на гибкой архитектуре, позволяющей легко изменять/добавлять бизнес-логику (новые ниши, гипотезы)<br>**N-08:** Система должна собирать всю необходимую информацию для первого контакта с квалифицированным лидом |

## L2. Системный Анализ: Требования к Системе

### Функциональные Требования (Что система делает)

*   **[REQ-F-01]:** Система должна инициировать диалог с пользователем и предложить выбрать отрасль бизнеса из предопределенного списка
*   **[REQ-F-02]:** Система должна последовательно запрашивать у пользователя его бюджет и основную маркетинговую цель, предоставляя варианты ответов в виде кнопок
*   **[REQ-F-03]:** На основе полученных данных (отрасль, бюджет, цель) система должна сгенерировать `MarketingPlan`, содержащий как минимум одну `Hypothesis`
*   **[REQ-F-04]:** Каждая `Hypothesis` в плане должна содержать: канал продвижения, целевой сегмент, ключевую потребность, выделенный бюджет, обоснование (`reason`) и прогноз по ключевым метрикам
*   **[REQ-F-05]:** Система должна представить сгенерированный `MarketingPlan` пользователю в структурированном и читаемом виде
*   **[REQ-F-06]:** После представления плана система должна предоставить пользователю единый, ясный призыв к действию (CTA) для связи с экспертом
*   **[REQ-F-07]:** При активации CTA система должна уведомить Владельца Системы, передав ему полный профиль запроса пользователя

### Требования к Интерфейсу (Как система взаимодействует)

*   **[REQ-I-01]:** Система должна функционировать в мессенджере Telegram
*   **[REQ-I-02]:** Весь основной путь пользователя (квест) должен быть реализован через интерфейс кнопок (Inline Keyboard) для минимизации ошибок ввода и упрощения взаимодействия

### Требования к Данным (С чем система работает)

*   **[REQ-D-01]:** Система должна оперировать доменной моделью, включающей `ClientProfile`, `Hypothesis` и `MarketingPlan`
*   **[REQ-D-02]:** Бизнес-логика (правила генерации гипотез, данные по отраслям) должна быть отделена от кода, отвечающего за диалог, для упрощения ее модификации (Удовлетворяет **N-07**)

### Нефункциональные Требования (Как хорошо система работает)

*   **[REQ-NF-01] (Производительность):** Время ответа системы на любое действие пользователя в рамках основного сценария не должно превышать 3 секунды
*   **[REQ-NF-02] (Надежность):** В случае внутренней ошибки при генерации плана система не должна "падать молча", а должна выдать пользователю корректное сообщение об ошибке и предложить попробовать позже или связаться напрямую
*   **[REQ-NF-03] (Конфигурируемость):** Добавление новой отрасли с ее сегментами, потребностями и правилами для MVP не должно требовать переписывания основной логики машины состояний

## L3. Логическая Архитектура (Abstract How)

### Структурный вид (Логические Блоки)

1.  **`Telegram Interface Gateway`**: Единственный блок, который "общается" с Telegram API. Принимает обновления от пользователя, отправляет сообщения и кнопки
2.  **`Dialog Manager (State Machine)`**: Ядро диалога. Хранит текущее состояние каждого пользователя (`AWAITING_BUDGET` и т.д.), обрабатывает входящие команды от `Gateway` и решает, какое действие выполнить дальше. Не содержит бизнес-логики
3.  **`Client Profile Service`**: Отвечает за создание, обновление и хранение `ClientProfile` в рамках сессии пользователя
4.  **`Hypothesis Generation Service`**: Мозг системы. Принимает на вход `ClientProfile`, обращается к `Business Logic Repository` и генерирует `MarketingPlan`. Полностью изолирован от Telegram
5.  **`Business Logic Repository`**: Хранилище знаний системы. Содержит данные по отраслям, сегментам, потребностям и, главное, правила для генерации гипотез (Для MVP это может быть простой JSON-файл или фикстуры в коде)
6.  **`Notification Service`**: Отправляет уведомление Владельцу Системы о новом квалифицированном лиде

### Поведенческий вид (Основной сценарий - Use Case: "Получение Маркетингового Плана")

1.  **Пользователь** → `Telegram Interface Gateway`: Нажимает кнопку
2.  `Gateway` → `Dialog Manager`: Передает команду и ID пользователя
3.  `Dialog Manager`: Определяет текущее состояние, передает данные в `Client Profile Service` для обновления
4.  `Dialog Manager`: Определяет следующее состояние и команду для `Gateway` (отправить новый вопрос с кнопками)
5.  ... (цикл повторяется до полного сбора данных) ...
6.  `Dialog Manager`: (когда `ClientProfile` собран) Вызывает `Hypothesis Generation Service` с `ClientProfile`
7.  `Hypothesis Service` → `Business Logic Repository`: Запрашивает правила и данные
8.  `Hypothesis Service`: Генерирует `MarketingPlan` и возвращает его `Dialog Manager`
9.  `Dialog Manager` → `Gateway`: Передает команду на форматирование и отправку `MarketingPlan` пользователю

## L4. Стратегия Верификации и Валидации (The Proof)

*   **Валидация (Делаем ли мы правильную вещь?):** Проводится путем демонстрации MVP стейкхолдеру "Марк" (или его представителю) для получения обратной связи на соответствие его потребностям (**N-01 - N-04**)
*   **Верификация (Делаем ли мы вещь правильно?):** Проводится путем тестирования на соответствие требованиям (**REQ-**)

### Матрица Верификации (Пример)

| Требование | Метод Верификации | Критерий Успеха (Acceptance Criteria) |
| :--- | :--- | :--- |
| **[REQ-F-04]** | **Тестирование (Test Case)** | При вводе `industry: b2b-logistics`, `budget: 150000` система генерирует план с 2-мя гипотезами (Директ, Telegram), корректно распределяет бюджет (60/40) и содержит непустое поле `reason` для каждой |
| **[REQ-NF-01]** | **Анализ Производительности (Load Test)** | Время от нажатия последней кнопки до получения первого сообщения с планом не превышает 3 секунды при 10 одновременных пользователях |
| **[REQ-D-02]** | **Инспекция Кода (Code Review)** | Правила генерации гипотез вынесены в отдельный конфигурационный файл/модуль и не находятся внутри `Dialog Manager` |
